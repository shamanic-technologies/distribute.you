# Dashboard v2 (`src/app/(authed)/v2/**`, `components/v2/`)

Design language, tokens, primitives, recipes, no-gos, render check: load skill `dashboard-v2-ux`. Below is architecture only.

GA since 2026-09-27 for every signed-in user: no allowlist gate, no beta badge (`tests/dashboard-v2.test.ts`). Every page is v2 (Today, Records, Work, Crew, Missions, person, offers + targeting, mission settings, integrations, brand settings, billing, API key, profile, invite).

- **Forks NOTHING in the data layer**: same providers (`QueryProvider`, `OrgContextProvider`, `FeaturesProvider`, `BillingGuardProvider`) and v1 query-key PREFIXES (`["brandRevenue", brandId, ...]`, `useCampaignRows(..., ALL_OFFERS)`). No v2 `api.ts`.
- **ONE offer per dashboard (owner 2026-10-03)**: the sidebar switcher picks an offer under the brand (`SelectedOfferProvider` in `v2-shell.tsx`, `components/v2/selected-offer.tsx`, cookie `distribute-offer-<brandId>` via alias-free `lib/v2/selected-offer.ts`; the URL's offer, or a mission's, wins and is remembered). EVERY brand page reads that offer only: money `getOfferRevenue` / `getOfferDealsValue` / `getOfferContactedValue` (features-service offer grain), leads `useLeadScope` (`brandId`+`offerId`), missions `useMissions` (`allOffers` only for pages addressed by a mission/run id and the offer's own page), runs via the offer's `campaignIds`, daily budget via `splitDailyBudget(..., inScope)`. A brand-wide total appears NOWHERE, on purpose; there is no list of offers (sidebar "Offer" = the selected offer's page; archived offers + Restore sit under it). A new brand read goes through these hooks; guard `tests/v2-selected-offer.test.ts`. Org-level facts (credit, billing, team) stay org-level.
- **Vocabulary**: CREW = one leg x one channel with a proper name (`lib/v2/crews.ts`, alias-free, unlisted pair named by its channel, never invented); MISSION = crew x offer = a campaign identity (no backend); audiences are rows inside a mission. Every channel has a name in `CHANNEL_NAMES`.
- **v1 is DELETED (2026-10-01; git history has it).** No version cookie, no Back to v1. `proxy.ts` redirects EVERY old v1 URL (`/`, `/orgs/**`, `/account`, `/api-keys`) to v2 pre-paint via `v2PathForV1` (`lib/ui-version.ts`, unit-tested): a page with a twin goes to it, anything else to the nearest v2 page above (brand, else org). Old URLs keep arriving (sent emails, Stripe returns, links inside embedded shared components), so never drop a `v2PathForV1` line. Headless side effects (signup/welcome notification, Stripe-return conversions, referral claim) mount in `v2-client-layout.tsx`, the only authed dashboard shell.
- **Forms embed v1 business components** (`setup-pages.tsx`; api-keys/account embed `components/settings/{api-keys-panel,account-profile}.tsx`). Never rewrite a settings form (two editors drift). A v1 component reading `params.id`/`params.offerId` takes an optional prop (`CampaignWorkflowsPage({campaignId})`, `CustomerAudiencesPage({campaignId, offerId})`). Embeds read as v2 through ONE layer: `keel.css` maps v1 utilities under `.v2-root .v2-embed` (`V2Page` wraps bodies; guard `tests/v2-embed-keel-layer.test.ts`); fix a v1 class family there, never per page. LIST pages are v2-native (owner 2026-09-28): Targeting + mission Audiences, Integrations render v2 markup over v1 readers/keys/writes.
- **Billing is v2-native** (`components/v2/billing-page.tsx`) over the SAME `useBillingController` as v1 (`components/billing/use-billing-controller.ts`; a charge path exists once). **The payment mode is a TAG, never a switch** (owner 2026-10-01): each org keeps the mode it has, only staff move it (admin console, billing's staff route); signup flows still set it once through `PUT /v1/accounts/payment_mode`. Owner rule: a control missing a prerequisite the page can supply OFFERS it on click, never a greyed card. **Revolut Business is the default acquirer** (owner 2026-09-29): `declareRevolutDefault()` (`lib/api.ts`, `/api/orgs/revolut`) runs before EVERY card/money call; an org with its card on Stripe stays (`card_elsewhere`). Revolut cannot save a card for $0 (released $1 auth): no "$0" copy. Guards `tests/revolut-default.test.ts`, `v2-billing-page.test.ts`.
- **"Needs your call" = `bucket=positive_reply&standing=sales_interest`** (`useNeedsYourCall`), never the standing alone (also holds site visitors: 86 of 87). Deals column reads "Interested".
- **`backdrop-filter`/`transform` makes a containing block for `position: fixed`**: top bar is opaque; ⌘K portals to `#v2-portal`; sidebar popovers stay within sidebar width.
- **Running is green** (`--run`), never the brand accent.
- **URL parsing**: Clerk `organizationPatterns` carry `/v2/orgs/:id` twins; `brandIdFromPathname` and `useTenantSwitcher` strip a leading `/v2`. A NEW anchored parser must `stripV2Prefix`. `/v2` -> active org -> last brand (cookie) else brand picker.
- **Three crews always listed on Crew** (`OFFERED_CREWS`, owner 2026-09-29): Herald (cold email, entry to Positive reply), Scout (cold email, entry to Website visit), Pilot (AI Meeting Booking, Positive reply to Meeting booked). Other names stay for staff campaigns; a working crew is always listed. `Add a crew` is staff mode only. Tag via `crewTrigger` (entry leg `[Daily] <outcome>`, else `[⚡ <step>] <outcome>`). **An event crew's budget is a CAP, not daily money**: every v2 daily figure (`CampaignControlsTrigger dailyOnly`, `useDailyBudgetSplit`) counts entry-leg crews only and states the cap beside it. Missions added via `AddMissionModal` -> `createCampaignForPair` (`lib/start-pair.ts`, shared with Offer Settings). Offer page 70/30 (offer left, missions right).
- **Crew/Work read runs-service** (`components/v2/runs.ts`: `getBrandRunsByCampaign`, `listBrandRunLedger`), filed under crews via `missionByCampaignId`.
- A company opens `/companies/[companyKey]` (domain, else features-service org id).
- **Sidebar menus copy Explee's** (`lab-static/explee-app/__menus`): switcher = brand rows + New brand, Offers + New offer (`V2NewOfferModal`), Organizations + New organization; account menu = email (Profile), Team (`/team`, read-only), API Keys, Billing, Refer a friend, Help (`supportWhatsAppHref`), Sign out. No Notifications/Feedback/Theme.
- **Team invites** (#4559): `POST /api/orgs/invitations` (Clerk invitation, `redirectUrl` = `/invite?org=<id>`). Our auth pages never read `__clerk_ticket`, so `/invite` (public, NOT an auth route) turns the ticket into sign-up/sign-in/accept, then activates the org. `clerk.distribute.you/v1/tickets/accept` 403s from the box IP: use a browser.
- Not served, so absent not computed: delivery rate, per-mission sends/reply rate, run success rate, median run time.
- **Staff mode: nothing below a Mission reaches a customer** (owner 2026-09-29, reversing 09-28 GA). `useStaffMode()` (`lib/use-staff-mode.ts`, cookie `distribute-staff-mode` in alias-free `lib/staff-mode-cookie.ts`, absent = ON) is the ONE staff gate: staff email AND the account-menu `Staff mode` switch. It gates sidebar Workflows, mission Workflows tab (`missionTabs(..., staffMode)`), crew card Workflows link, Research entry, all-orgs tenant list, Mature/Flash + User/Actual switches (`useStatBasis`/`useCostBasis`), prompt Edit, run page Workflow/Version/LLM/Template rows. Pages (`workflows/**`, `research/**`, `monitoring/**`, mission workflows) sit behind `<StaffOnly>` (`components/v2/staff-only.tsx`, renders nothing until Clerk resolves). `<StaffOnly>` hides the UI ONLY: a staff page's DATA comes from an `isAdminEmail`-gated server route, never a client-bundled import (Research JSON shipped in the bundle until `/api/research/{basis}/{part}`), or from a gateway `requireStaff` route through the `/api/v1` proxy (Monitoring: `STAFF_MONITORING_PATHS` in `lib/api.ts`, roots in `SENSITIVE_QUERY_ROOTS`). Staff surfaces carry NO `staff` tag; a NEW staff surface reads `useStaffMode().staffMode`, never `useIsAdminUser` alone; customer copy never says workflow/model/template. Workflow page: a row is a workflow FOR ONE CREW; Brand grain = ladder at the crew's leg with NO campaign (Global `crossOrg`, Brand `brand`); past runs = runs-service by VERSIONED slug + `taskName=execute-workflow`, emails `/v1/emails?runId=`; row panel is a `drawer`.
- **Monitoring counts are bar charts over time with a Daily/Weekly/Monthly switch, never a lone total** (owner 2026-10-01). Emails: what reached LEADS (instantly-service `messages.kind` outreach) is separated from our own mail (warmup, warmup replies, seed/inbox-placement tests); the split is served per kind by the producer, never filtered here. **Monitoring's Cost section shows what vendors charge US, nothing else** (owner 2026-10-01): no billed price, markup, margin or unpriced-spend figure on a Cost page (guard in `tests/monitoring.test.ts`); a "real cost of X" page (email sending) lives under Cost. Per-item detail opens in a side panel, not a sibling page.
- Guards: `tests/dashboard-v2.test.ts`, `tests/v2-workflows-pages.test.ts`, `tests/staff-mode.test.ts`.
