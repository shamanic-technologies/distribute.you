# Leads: grain, status, timeline, board

## Showing a fact and stating it are different affordances
A map/chart/bar beside text that already prints the data is NOT duplication; the question is whether the picture reads faster. Do not answer a visual request with "we already display it", and size cost objections against real usage (4 users) before raising them. Real concerns are the visual's own (dependency, data leak to a tile server, dark theme). Cost 2026-09-04 (#3890): asked for a Location map, argued instead; shipped as inline SVG, zero requests, text rows kept.

## Table grain is not the endpoint's grain: read the response, never the schema
`leads_campaigns` is `UNIQUE(lead_id, campaign_id)` but lead-service collapses brand/org-scoped reads to ONE row per person (`DISTINCT ON (lead_id)` in `lead-list-query.ts`) with the BRAND-wide delivery roll-up. A feature designed to fan out over rows the endpoint already collapsed renders one of everything and looks right. Verify by one authenticated call to the polled endpoint; a `psql` count proves the opposite.
- Multiplicity is SERVED opt-in: `?include=campaigns` (lead-service v0.67.0) nests one card per membership row with `delivery` (`null` = provider holds none, never "nothing happened"), `standing`, `offer`, `audienceId`, `campaignIds`. Top-level delivery fields stay the brand-wide roll-up (badge, tabs, board read them).

## A status label states what HAPPENED, not what we ATTEMPTED
- `contacted` = handed to Instantly, not emailed (weekday 08:00-17:00 window in recipient tz, `America/Chicago` default; instantly retry sweep waits 72 h). `leadStatusLabel("contacted")` = `Queued` (slate); badge, table Status and CSV all read it.
- **Ladder is most-advanced-first and a BOUNCE outranks the send it failed** (and `unsubscribed` outranks `delivered`): `replied > clicked > bounced > unsubscribed > (opened) > delivered > sent > contacted`. `LEAD_STATUS_ORDER` must list the SAME order; its copies (dashboard `lib/api.ts` + three admin) move together (#3884). When a first-match ladder ranks CO-OCCURRING states, ordering is the whole function.
- Every row states its own status on every tab (`forceContacted` is gone: it made a sent lead read Queued).
- **Timeline is GROUPED BY MESSAGE**: each message (`kind: "message"`) is a bordered openable card (tint + 1px full border) with its own delivery rows inside. Only `Sent`/`Delivered` nest under the initial email; `Website visit`/`Replied`/`Bounced`/`Unsubscribed` stay TOP-LEVEL (wire carries lead-level first-occurrence timestamps, a reply may follow follow-up 2). Follow-up cards carry NO delivery rows (no per-step data; do not invent). A message card prints no date of its own when it has delivery rows (still sorts at that instant); a scheduled follow-up states its projected date. While `firstSentAt` is absent the queue row is the only delivery row (`queuedOnly` ternary) with `SEND_WINDOW_NOTE` on an `ⓘ`.
- **Row spacing keys on INDEX (`i < sorted.length - 1 ? "pb-4" : ""`), never `last:`** (`last:` is `:last-child` of the PARENT; the content div is always the last child of its `<li>`, so padding never applied).
- No `servedAt` footer (only `leadDateForStatus` while `Processing`). Instants via alias-free `lib/friendly-datetime.ts` (`Today at 8:45am`, local-midnight diff, hand-assembled time because ICU uses U+202F, future instants get a calendar date with NO clock time, no `Tomorrow`; `title` keeps full locale string). A timestamp derived from generation time is an offset (`estimate: "~Nd after the first email"`, no `title`).
- **CSV is lead-service's file** (`?format=csv`, headings in the customer's words as of v0.70.0, via `apiCall` `responseType: "text"`; `leads-csv.ts` deleted). Lost vs old: `Global bounced`, `Global unsubscribed`. Export asks through `leadsExportQuery({ search })`: NO bound, NO tab, `bucket=REACHABLE_BUCKET` (the same constant the header count uses), so file = reachable population (a builder reused from the page carried `limit=50` and truncated; a tab-scoped export contradicted the header). Pin the QUERY in a unit test, not that the reader is called. `apps/admin` keeps `Contacted` (staff raw state) in all four copies.
- Before naming a status ask whether the value proves the event or only that we tried (#3089).
- **Email copy is GA for every message** (owner 2026-09-25, reversing #4226): no gate, no badge, `LeadHistoryTimeline` takes no copy flag, no `.filter(` over rows. Two rules over one concept was the bug. `hasSalesInterest` (`lib/lead-sales-interest.ts`) survives for other readers; `Follow up now` stays beta (#4414). Guards `tests/lead-email-copy-gate.test.ts` (pins ABSENCE of gate), `tests/lead-history.test.ts`.

## A status and a date side by side are one statement
Date column is per-row status, not per-tab: `leadDateForStatus(lead, status)` (`lib/api.ts`, exhaustive `switch` over `LeadConsolidatedStatus`) maps badge to proving timestamp (`firstRepliedAt` / `firstClickedAt` / `firstDeliveredAt` / `firstSentAt` / `firstBouncedAt` / `firstUnsubscribedAt` / `firstContactedAt` / `servedAt`). `leadDateForTab` is DELETED; do NOT add a second date under the badge (#3152 did, reverted). `skipped/claimed/buffered` => `null` => `-`. Outcome tabs use the `/revenue` outcome instant. Guard `tests/lead-status-date.test.ts`.

## People page reads ONE PAGE at a time (v2 `people-page.tsx`; `lib/leads-server-page.ts`, alias-free, ONE home of the producer vocabulary)
Holding the population was 44MB / 99MB per brand, above `MAX_PERSISTED_ENTRY_BYTES`, so the table cold-loaded every visit. Two small reads, both in `PERSISTABLE_QUERY_ROOTS`:
- `["leadBucketCounts", scopeKey, wireSearch]` -> `GET /orgs/leads/bucket-counts` (163 bytes) and `["leadsPage", scopeKey, activeTab, wireSearch, page]` -> `GET /orgs/leads?bucket=&sort=activity&limit=&offset=`.
- Tab->bucket map is many-to-one: `meetings` = BOOKED meeting (reads **Meeting booked**), `sales` reads **Close won**, the board's words.
- `/revenue` is read only for the outcome DATE per row and which outcome tabs EXIST, never MEMBERSHIP (lead-service buckets outcomes off the same attributed ledger features-service prices; verify if a tab and its stat card diverge).
- **Header count = the CONTACTED bucket (`REACHABLE_BUCKET`), NOT `bucket-counts.total`** (total includes no-evidence rows no tab can show, #3071). Buckets are not exclusive: never sum them.
- Nothing counts rows in memory: an unstated tab size renders NO number (not `(0)`), pager counts over `total`, search "N of M" is the producer's.
- Order is the producer's `sort=activity` (total order, ties on row id); `sortByStatusDate` is DELETED (sorting one page reads as sorting the tab). Search is server-side over the whole population, debounced (300ms) and refused LOCALLY when lead-service would 400 (blank, >200 chars, >8 words; a 400 empties the table). Pager sends `offset` (numbered pages need it), not `cursor`.
- **Export**: see the CSV bullet above (`leadsExportQuery`, no bound, no tab). Both builders share `leadsScopeQuery`. A guard asserting a reader is CALLED says nothing about what it SENT: pin the query in a unit test.
- Guards `tests/leads-server-page.test.ts` (unit) + `tests/leads-server-paging.test.ts` (call sites) (#3861).

- **"Not contacted" while the provider sent = BACKEND bug**: do NOT widen a tab predicate. Diagnose with `GET lead.distribute.you/orgs/leads?brandId=` (valid-UUID `x-run-id`): an EMPTY `email` is the tell (overlay keys on `lead_contact_methods`; email-uniqueness clash, sales-lead-service#394).

- **Campaign-scoped leads reads are BRAND-SIZED: both readers send `view=basic`** (`tests/campaign-leads-endpoint.test.ts`). An infinite skeleton can be the GATEWAY OOM-dying: read `docker logs distribute-api-service-1` first; api-service must stream (`pipeExternalService`), never parse-then-re-serialize. `GET /v1/leads` forwards its query verbatim (v0.98.6).

## Lead BOARD = a TRIAGE (`lib/lead-board.ts`, alias-free; drawn read-only by v2 `deals-page.tsx`)
Answers "is this one still in play, and if not why", not "how far along". Steps are stated on the person page (cost + value live there; no drag-to-book). Columns: `Leads` · `Sales interest` · `Close won` · `Disqualified` · `Opt-out` · `Not placed` (`hideWhenEmpty`); no leg, so it renders at brand level too. Tabs and board coexist: tabs are nested subsets (counts overlap), the board is a PARTITION.
- **One count and one page PER COLUMN**: `GET /orgs/leads/standing-counts` + `?standing=` (comma-separated set). Column size = producer counts ADDED over the standings it holds (`boardColumnTotals`; `null` while unsettled). Seven standings, five columns (`STANDINGS_BY_COLUMN`); `not_contacted` is in NO column (columns never sum to `standing-counts.total`); a guard requires `STANDINGS_BY_COLUMN` and `leadBoardColumnFor` to agree. Growing a column asks for a WIDER page (`shown` in the key), never an offset. A card is placed by the column it was READ from (no second `leadBoardColumnFor` opinion), except a just-made statement. Counts first; empty columns are not fetched. `leadStandingCounts` persisted. `LEAD_BOARD_CARD_CAP` is gone.
- **Placement is lead-service's (standing).** `opted_out` is a STANDING (sales-lead-service#502); a `disqualified` row whose signal is an unsubscribe still reads as opt-out. **Disqualified = NOT OUR TARGET** (wrong person, changed job, wrong company; owner: "pears to supermarkets, emailed a construction worker"); `Not interested` stays in **Leads** (a no is where the conversation starts), a BOUNCE stays Contacted, a REFERRAL ("Not them, but points us on") is NOT sales interest. The fine split lives in instantly-service (`lead_not_interested` vs `lead_wrong_person`/`lead_changed_job`) and travels via email-gateway to lead-service; the dashboard re-decides NOTHING (a dashboard re-split was deliberately not shipped). `unresolved` / `reply_disqualification_unknown` is a real answer -> "Not placed".
- **Fine kind outranks coarse**: lead-service serves coarse `replyClassification` (+`unsubscribed`, `bounced`); instantly-service the fine kind. Precedence opt-out > disqualified > interest > contacted. The board reads the FINE kind while stat cards (`recipientsRepliesPositive`) read features-service's count over instantly's FROZEN kind->coarse map: changing a kind's column means grepping instantly-service's coarse map in the same breath (+ backfill). "Worth reading" (forwarded) vs "buying signal" (positive) differ: referral is forwarded but `neutral`.
- **A kind listed ahead of the catalogue is filtered SILENTLY by `columnReplyKinds`**: add a guard that FAILS once the producer serves it (`lead_changed_job` sat unrendered, #3818). `ManualQualificationStatus` reads `ReplyKind` (+2 retired spellings), never a re-listed copy.
- **`Close won`** = the `customer` standing. A sale is stated via `CloseWonForm` (`components/leads/close-won-form.tsx`, ONE form, mounted by v2 `person-page.tsx`; `step: "sale", kind: "outcome"` via `useSetAnyLeadStepStatement`).
- **A const a `useMemo` reads must be declared ABOVE it** (one declared below was a TDZ `ReferenceError` on mount with tsc/tests green); guard with an index compare (#3905).
- Reply-kind pills need dark remaps for text/border weights (`text-green-700`, `border-green-200`, `text-red-600`, `border-red-200`) as well as fills.
- Guards `tests/lead-board.test.ts`, `tests/lead-close-won-column.test.ts`.
